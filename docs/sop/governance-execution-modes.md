# governance-execution-modes.md

> **本文件是治理细则真源**（2026-10-22 自 `AGENTS.md` 下沉，内容原文搬运、未删规则）。
> 触发条件：读它的人是**编排者与主开发者**：两种执行方式的完整口径（含「你是主开发者」口令、连续推进、子代理模型口径）。
> 不需要本文件时**不要读**（省上下文）——`AGENTS.md` 只留红线与索引。

- **触发口令（2026-10-17 用户定改名）｜「你是主开发者」**（旧口令「**你是唯一开发者**」保留为**同义别名**，仍然有效，不失效、不改历史记录）：用户说出**这一句即立即启用 ORCA 主开发者模式**。**为什么改名**：「唯一」二字把执行人数锁死了，长期被理解成「只能一个人串行干活」，于是子代理并行被误禁用 —— 而这条口令真正要表达的是**身份（你是这个项目的主责开发者、治理角色由你兼任）**，不是人数。**该模式下你不是编排者（task-manager）**：不做角色派工与阶段编排、不启动治理角色链、不记 DISPATCH 派工行；**但记账与 HANDOFF 交接照旧**（自己给自己记账，不是免账）。①**无需用户再补充任何其他启动提示词**，**不得再次询问**是否启用，**不得自动派遣其他治理角色**（但**允许并鼓励派子代理并行推进可并行的子任务**，见下方「主开发者」条）；②**智能体自行**根据项目当前状态，按需查找、读取并执行现有规范——产品规划与简化审查、UI 设计与交互规范、SDD 与开发任务、对应技术 SOP 与 Skill、Code Review 自审、真实 QA／缺陷修复／复验、HANDOFF 与最终交付；③**由 ORCA 自动决定各阶段读哪些文件，用户不负责逐项指定规范**；④**口令只决定执行方式，不代表跳过产品方案确认、必要 Human Gate 或授权要求**（见下方 Human Gate 条）。
- **体系管家（2026-10-27 用户定，原名「治理管家」）**：口令「**你是体系管家**」**不是第三种执行方式**，而是接管**整套 ORCA 治理体系的内容管理与修改**（`AGENTS.md`／`docs/sop/`／`docs/roles/`／`scripts/`／模板／两包同步／`ORCA治理体系说明.md`／体系专线 HANDOFF）；可与主开发者或多智能体**叠加**，项目内执行方式仍由原口令决定，不派治理角色链。红线照旧：不 commit／push、不批量铺包、不改质量门判定与账本 schema。
- **多智能体（默认）**：本文件其余各节全部适用——角色分工、独立审查、Supervisor 复检、Task Manager 派工与账本，**维持原样，不因本节改动而降低**。
- **主开发者（原单智能体模式（旧称），同一口令）**：主开发者负责产品设计、开发、代码自审、QA 与交付。①**不派治理角色链**（不启动 code-reviewer／qa／supervisor／product-reviewer／planner 这些**角色身份**的多智能体派工），**但允许、且鼓励用子代理并行推进执行任务**——**2026-10-17 用户澄清（此前理解过窄）**：这个模式的含义是「不完整走 ORCA 多角色治理」，**不是「只能一个人串行干活」**。该智能体应**自己判断哪些子任务互不依赖、可并行**，对可并行的部分派子代理同时推进（子代理是执行并行，不是治理复核），串行依赖的部分才自己做；**不得因为客户端支持子代理就无脑全派**，也**不得因为该模式就放弃并行**；②`docs/roles/` 里「禁止兼任／独立 Session／独立派工」等要求**只约束多智能体执行**，主开发者可按阶段引用这些角色的**质量标准**；③结论必须**如实标注**是「自审」（开发智能体自己检查）还是「独立审查」（确有其他执行者独立审查），**不得伪造独立审查结果**。
- **主开发者模式的执行层／判定层分界（2026-10-17 用户定）**：
  - **执行层可外包给子代理**：跑测试、跑构建、起服务点关键路径、真机 adb 操作、截图取证、按清单逐项核查**现象** —— 这些天生可并行，**应该派子代理同时推进**。
  - **判定层不外包**：`PASS`／`FAIL`／`DEGRADED` 的判定、宣布收工、产品验收追踪矩阵里关键 AC 的结论、首次发布签收 —— **全部由主开发者自己拍**，因为它承担后果。
  - **子代理的产出必须附可核查证据**（命令与输出、真机截图路径、实际观察到的现象），落 `docs/qa/<交付单元>/` 作**证据来源**引用；矩阵结论由主开发者引用这些证据后自己写。**子代理不是独立审查者，标注不许拔高**（结论仍写「自审」）。
  - **关键路径主开发者至少亲手复验一次**，不得全凭子代理 —— 我们栽过「exit 0 ≠ 操作成功」「href 全在但点击零变化」两个坑，子代理最擅长把「跑完了」说成「通过了」。
  - 记法：子代理的活**不单独记账本行**（账本只记主开发者这一层，否则污染换模型依据的统计），在 HANDOFF 里记一句派了什么、证据在哪。  - **子代理的模型与推理强度怎么定（2026-10-17 用户定，因 043 实跑暴露的规则缺口而补）**：此前只规定「可以派子代理并行」，**没规定子代理用什么模型和强度**，于是每个项目只能各自解读、还会被误写成「按模型调度规则选的」。现定口径**按平台分两种，只有 GPT 一侧才讲模型映射**：

    | 平台 | 口径 |
    |---|---|
    | **GPT（Codex 系／桌面版 GPT）** | 派子代理**能显式传 model／effort** ⇒ **应当显式指定，并优先用本体系分工表里的模型**（见下面映射表）。这是**省额度**的主要手段：别让子代理默认继承主线程那个贵模型 |
    | **WorkBuddy／Qoder／CodeBuddy sh／opencode 等其他智能体与开发平台** | **一律继承主开发者模型**——主开发者用什么，子代理就用什么。**不要求指定、不套用下面那张映射表**（它们的派工接口本就没有 model 参数，写了也是无法执行的规则） |

    1. **其他平台默认继承主线程**：派单里**不必**指定模型，也**不必**声称是按分工表选的；交接里如实写「继承主开发者模型」即可；
    2. **仅当客户端支持显式传 model／effort（即 GPT 侧）才走下面第 3 条的映射**；
    3. **GPT 侧按「子代理实际干的事」取行**（`USER_MODEL_OVERRIDE.md` 对应角色行，通道与调用方式照该行）：

       | 子代理在干什么 | 取哪一行 | 现役模型 |
       |---|---|---|
       | 写代码、改代码、修 bug、加测试用例、构建/发布脚本 | `builder` | **`opencode-go/deepseek-v4.1-flash`** |
       | 写文档、规则、SOP、模板、交接与注释 | `builder`（文档也是执行产物，不另设行） | 同上 |
       | 跑测试、跑构建、起服务点关键路径、真机 adb、截图取证、按清单逐项核查**现象** | `qa` | `codex/gpt-6-luna` |
       | 只读研究、竞品/参考资料调研、出**意见**（不落盘决策） | `product-reviewer` | `codebuddy/glm-5.3-flash` |
       | 数据库 schema 审查（只读出审查结论） | `db-admin` | `volcengine-plan/ark-code-latest` |
       | **复核、判 PASS/FAIL、宣布收工、写关键 AC 结论、首次发布签收** | **不外包** | 由主开发者自己做 |

       为什么执行层在 GPT 侧统一用 `opencode-go/deepseek-v4.1-flash`（不再按「并发/非并发」分档）：
       ①**订阅通道无按频率限额**——codebuddy 按频率限额，builder 355 次派工集中在单账号，撞 429 是必然（043 实测到要等约 20 小时）；
       ②2026-10-07 实测 codebuddy **双实例并发互相干扰、被抢的一方静默失败 exit 0 零产出**。
       **少一个判断点、少两个坑，收益大于「模型多样性」那点好处**。codebuddy 通道留给多智能体模式的 `builder` 角色。
       **例外**：真机 adb／取证仍走 `qa` 行的 `codex/gpt-6-luna`（codex 通道，不受 codebuddy 限额与并发问题影响）。
       **为什么 product-reviewer 行可用于只读调研子代理**：该行口径本身就是「只读研究、禁写业务代码与改 Plan」；
       但它**只出意见、不出决策**。`planner`（`codex/gpt-6.1-terra`）／`senior-expert`（`codex/gpt-6.1-sol`）两行**成本最高、留给判定层**，
       执行层子代理默认不用。
    4. **禁把治理角色映射给子代理**：`code-reviewer`／`planner`／`product-reviewer` 行**不得**用于执行层子代理（判定层本就不外包）；
    5. **禁无记录降级**：为省额度把子代理降到明显更弱的模型或更低强度，可以，但**必须在 HANDOFF 写明「派了什么／用什么模型与强度／为什么这么分」**——不许默默降级；
    6. **不许声称**：若只是继承主开发者模型、并未查分工表，就**如实说「继承主开发者模型，未做模型成本分档」**，不得写成「按一套完整的模型调度规则选出」。


- **用户明确指定主开发者模式时直接采用，不再询问**，也不得自行改回多智能体；**用户没有要求切换模式时，不得擅自改变既定执行方式**。
- **原有 Human Gate 同样适用（2026-10-10 复审明确，不新增 Gate）**：主开发者模式连续推进**不得绕过**①开发前必要的产品方案批准；②重大需求或安全边界变更的 Change C 受控重开；③**首次发布用户签收**；④生产操作、付费、凭据、不可逆操作等原有授权限制。**以上均为既有规则在主开发者模式下的继续适用，不是新加的关卡。**
- **不降低质量门禁**：产品简化（`docs/sop/app-simplicity.md`）、APP 基础能力（主题／中英双语／品牌资产／导航／信息分层）、**安全、隐私、异常恢复与数据正确性、真机验收、首次发布用户签收、产品验收追踪矩阵**在主开发者模式下**一条不减**；QA 必须**真实运行应用并操作关键功能**，没有实际验证的项目**不得直接标 `PASS`**。**但各项检查按项目类型、实际工具与风险适用**——真机 Canary、QA 会话能力预检只在对应工具与测试方式适用时强制，**不得因缺少与本项目无关的工具而阻断正常开发**（细则见 `docs/roles/qa.md`「主开发者模式的 QA 执行细则」）。**主开发者模式不模拟 supervisor 独立角色，但交付前必须逐条检查原有关键质量放行条件**（关键 AC 全有证据并通过／首次发布已签收／无 P0 未完）。
- **减少的是管理成本，不是质量成本**：①不强制创建多角色派工记录（`DISPATCH-LOG.jsonl` 无派工就留空，**不造行**）；②不强制逐个模拟 Builder／Reviewer／QA／Supervisor；③**普通局部修改不重走完整产品规划**；④任务简单时允许简短计划、简短自审、必要 QA 证据（**报告规模与风险相称，不强制产出与风险不相称的报告；实际测试一步不能省**）；⑤**计划已批准后可连续开发→自审→测试→修复直到任务完成**，QA 发现问题由同一智能体切回开发修复再复验，**只在遇到真正需要用户授权的事项（secrets、不可逆删除、生产／他人项目、commit／push）时才暂停**。
- **自审仍须留痕，但留痕粒度＝交付单元**（2026-10-17 用户定）：`docs/review/`（照 `CODE_REVIEW.template.md`）与
  `docs/qa/`（照 `BUGS.template.md`）**在交付单元边界产出一次正式报告**；单 task 阶段只留极简结论一行
  （可先记在 HANDOFF 里，到边界再整理成正式报告），执行者是自己，标注口径不同而已。
  **两账本的 result 漂移已由 `check-ledger` 的 `LEDGER-XREF` 自动对账，禁止再手工 md5 比对两本账** ——
  那是纯人力且机器已覆盖的动作。`docs/qa/产品验收追踪矩阵.md` 的证据要求不变。**已铺包的项目这是硬要求，不因活小豁免**（见「小活豁免只管还没铺包的项目」条）——留痕可以是极简三五行，**但不能没有**；`TASK-MODEL-LOG.jsonl` 记一行（`DISPATCH-LOG` 仍可不造行）。
- **主开发者按阶段该读哪些规范**：见根 `README.md`「主开发者开发使用说明」（按需读，不许开工就全量加载角色卡与 SOP）。
- **不新增第二套体系**：不新增主开发者专属角色／Gate／Skill／Reviewer／QA SOP／模板包；两种执行方式共用同一套规范与模板包。
